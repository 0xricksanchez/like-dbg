# B2 — x86_64-on-Mac (in-container TCG debuggee) — Design

**Date:** 2026-06-23
**Status:** approved (brainstormed)
**Branch:** `feat/b2-x86_64-mac` off `dev` → merged **locally** (per ROADMAP: `dev` stays local)
**ROADMAP item:** §B foundation-completion, piece 2 of 3 (after B1; builds the in-container launch
seam that B3 will reuse). ADR-0001 keeps x86_64-on-Mac in-container TCG.

## 1. Context

The CLI runtime is native-HVF-only today: it always launches QEMU as a host process and a gdb that
hardcodes the aarch64 architecture. For x86_64 on the Mac, ADR-0001 mandates **in-container TCG**
(a Linux container can't reach macOS HVF). The detection is already done — `host_profile.detect`
returns `debuggee_mode="in-container"`, `accel="tcg"` for x86_64-on-Mac, and `qemu.py` already emits
correct x86_64-TCG argv (`qemu-system-x86_64`, `-cpu qemu64,+smep,+smap`, `console=ttyS0`,
`-accel tcg`). The `.dockerfile_dbge` debuggee image already bundles the QEMU binaries
(`qemu-system` package) and a qemu healthcheck. What is missing is the **wiring**: an in-container
QEMU launcher, the launch dispatch, an arch-aware gdb invocation, and gdbstub addressing for a
containerized gdb reaching an in-container QEMU.

**Scope (decided): full x86_64 boot to userspace** — build → foreign-arch rootfs → in-container TCG
boot → containerized gdb at `start_kernel` and through to systemd userspace.

## 2. Decisions (resolved during brainstorm)

- **gdbstub networking = publish-to-host.** The debuggee container runs `qemu … -s` with
  `docker run -p 1234:1234`; the debugger container reaches it at `host.docker.internal:1234` — the
  same address the native-HVF path already uses, so one attach model across both. (Refines ADR-0001:
  on **macOS** in-container uses `host.docker.internal`; "localhost/shared-net" stays the Linux/B3 story.)
- **Image manifest: add debuggee; run-required set is per-path AND per-mode.** `IMAGES` grows to 5;
  `images.required_for(host)` returns the debuggee only for in-container runs.
- **Identical-path mounts** keep `build_qemu_argv` mode-agnostic.
- **Full x86_64 boot to userspace** is the completion bar (foreign-arch debootstrap included).

## 3. Component design

### 3.1 `qemu_container_command` (new, `src/likedbg/launchers.py`)

The in-container sibling of `qemu_pane_command`. Signature:
```python
def qemu_container_command(argv: list[str], *, image: str, mounts: list[Path], gdbstub_port: int = 1234) -> str:
    binds = " ".join(f"-v {shlex.quote(str(p))}:{shlex.quote(str(p))}:ro" for p in mounts)
    docker = f"docker run --rm -it -p {gdbstub_port}:{gdbstub_port} {binds} {image} "
    return docker + shlex.join(argv)
```
- **Identical host→container bind mounts** (`-v <p>:<p>:ro`) so the QEMU argv's embedded host paths
  (`-kernel <Image>`, `-drive file=<rootfs>`) resolve unchanged inside the container. Feasible: the
  exported `Image` and rootfs live under `/Users/...`, which colima shares into the VM.
- `-p 1234:1234` publishes the gdbstub to the host; `-it` + QEMU `-nographic` route the serial
  console to the tmux pane (same pattern as `gdb_pane_command`).
- `shlex` quoting mirrors the existing launchers (multi-word `-append`/paths survive the pane shell).

### 3.2 Launch dispatch (`DebuggeeStage` + `cli.py`)

`DebuggeeStage.run` passes the mount sources alongside the argv:
```python
argv = build_qemu_argv(ctx.settings, ctx.host, kernel_image=ctx.kernel_image, rootfs=ctx.rootfs_image)
mounts = [p for p in (ctx.kernel_image, ctx.rootfs_image) if p is not None]
self._launch(argv, mounts)
```
The `launch` callable signature becomes `Callable[[list[str], list[Path]], None]`. `cli`'s
`launch_qemu` closure (in both `build_pipeline` and `build_use_pipeline`) branches on the captured
`host.debuggee_mode`:
```python
def launch_qemu(argv: list[str], mounts: list[Path]) -> None:
    session.select_pane(debuggee_pane)
    if host.debuggee_mode == "in-container":
        cmd = qemu_container_command(argv, image=debuggee_image, mounts=mounts)
    else:
        cmd = qemu_pane_command(argv)  # native host (unchanged)
    session.send_keys(cmd)
```
`build_pipeline`/`build_use_pipeline` gain `host: HostProfile` and `debuggee_image: str` params so
the closure can branch and name the image.

### 3.3 Arch-aware gdb (`src/likedbg/gdbcmd.py`)

`build_gdb_args` gains an `arch` parameter and maps it to the gdb architecture string:
```python
_GDB_ARCH = {"arm64": "aarch64", "x86_64": "i386:x86-64"}

def build_gdb_args(host: HostProfile, *, arch: str, vmlinux: Path, ext: str, breakpoint: str | None) -> list[str]:
    ...
    args += ["-ex", f"set architecture {_GDB_ARCH[arch]}"]
    ...
```
`DebuggerStage` passes `arch=ctx.settings.general.arch`. The `addr`/`hbreak`/`gef-remote`/`target
remote` logic is unchanged. (Today's hardcoded `aarch64` is a latent x86_64 bug.)

### 3.4 OS-based gdbstub addressing (`src/likedbg/host_profile.py`)

Replace the mode-based `addr` with OS-based:
```python
addr = "localhost" if os_name == "linux" else "host.docker.internal"
```
On macOS, gdb is always containerized and reaches QEMU via the host — the host process (native-HVF)
or the published container port (in-container). On Linux (B3), `localhost`/shared-net. This keeps
arm64-native (`host.docker.internal`) unchanged and makes x86_64-in-container reach the published port.

### 3.5 Debuggee image in the manifest (extends B1 / ADR-0004)

- `constants.py`: add `DEBUGGEE_IMAGE = "like_debuggee:latest"` (spelled out, to avoid confusion
  with the `like_debugger` image; built from `.dockerfile_dbge`).
- `images.py`: add a 5th `ImageSpec(DEBUGGEE_IMAGE, ".dockerfile_dbge", (".dockerfile_dbge",), {"USER": "user"})`
  to `IMAGES` (so `--build-images` builds it and the completeness guard covers its dockerfile).
- `images.py`: add `required_for(host: HostProfile) -> tuple[ImageSpec, ...]` — the existing four
  always, plus the debuggee spec iff `host.debuggee_mode == "in-container"`.
- `cli.py`: the build-run `_ensure_images` uses `images.required_for(host)` (not the flat `IMAGES`).
  Arm64-native stays at 4 and never builds the debuggee. (`USE_IMAGES` is unchanged for now —
  `--use` in-container is a later concern; B2 targets the full build-run.)
- The justfile already delegates to `--build-images`, so it gains the debuggee with no edit.

### 3.6 Foreign-arch rootfs (scope b)

The infra exists: `.dockerfile_rootfs` installs `qemu-user-static` + `binfmt-support`; `rootfs.sh`
mounts `binfmt_misc`, registers QEMU handlers (`qemu-binfmt-conf.sh`), and runs `debootstrap
--foreign` for the cross-arch case (`RootfsStage` passes `-a x86_64` → `--arch=amd64`). B2's task is
to **validate the amd64-on-arm64 build live and fix-forward** the likely failure: the `--foreign`
*second stage* needs `qemu-x86_64-static` resolvable inside the chroot. The fix, if required, is a
small `rootfs.sh` change — register binfmt with the `F` (fix-binary) flag (add `-p`/persistent to the
`qemu-binfmt-conf.sh` invocation) **or** copy `qemu-$ARCH-static` into `$MNT/usr/bin` before
`--second-stage`. Editing `rootfs.sh` changes the rootfs image's `input_sha` (it is a `build_inputs`
file), so B1's stale-WARN/`--build-images` flow correctly forces the rebuild.

## 4. Regression safety (arm64-native-HVF unchanged)

Every arm64 axis is untouched and unit-asserted: launch path (`qemu_pane_command`), gdb architecture
(`aarch64`), gdbstub addressing (macOS → `host.docker.internal`), and the run-required image set
(4 images, no debuggee). B2 is additive for the x86_64/in-container path plus the gdb-arch
generalization (arm64 still maps to `aarch64`).

## 5. Testing strategy

Unit (tests in `./tests/`):
- `qemu_container_command`: builds the expected `docker run` string — `-p 1234:1234`, identical-path
  `:ro` binds for each mount, the image, then the argv; rootfs omitted when not in `mounts`; shlex
  quoting of paths/argv.
- Launch dispatch: with `debuggee_mode="in-container"` the closure emits a `docker run …` for the
  debuggee image; with `native-host` it emits the plain native argv (existing behavior).
- `build_gdb_args`: `arch="x86_64"` → `set architecture i386:x86-64`; `arch="arm64"` → `aarch64`
  (regression); addr/hbreak/remote lines unchanged.
- `host_profile`: macOS + in-container + tcg → `gdbstub_addr == "host.docker.internal"`; macOS +
  native-host → `host.docker.internal` (regression); Linux → `localhost`.
- `images`: `IMAGES` has 5 specs incl. debuggee; completeness guard covers `.dockerfile_dbge`;
  `required_for(in-container host)` includes the debuggee, `required_for(native-host host)` does not.
- Gate: `uv run ruff check src tests`, `ruff format --check`, `uv run mypy src/likedbg`,
  `uv run pytest -q` all green.

## 6. Live-gate verification (M5)

1. `uv run ./start_kgdb --build-images` builds all 5 images incl. `like_debuggee:latest`.
2. With an x86_64 config (`[general] arch = x86_64`): `uv run ./start_kgdb` builds the x86_64 kernel
   (clang), builds the **foreign-arch (amd64) rootfs**, launches **in-container TCG** QEMU, and the
   containerized gdb hits `hbreak start_kernel` (architecture `i386:x86-64`), then boots through to
   **systemd userspace** with a runtime breakpoint (e.g. `break schedule`). This is the scope-(b) bar.
3. **No-regression:** an arm64 config still build→boot→debugs via native-HVF exactly as before
   (host QEMU, `aarch64` gdb, no debuggee image built).
4. Confirm no leftover helper containers (B1 `auto_remove`) and the debuggee container is `--rm`'d.

## 7. Non-goals

- **Linux/bind runtime (B3):** OS-based addressing leaves `localhost` for Linux, but B2 does not wire
  in-container-on-Linux or `/dev/kvm`; `require_volume_mode` stays.
- **`--use` in-container:** B2 targets the full build-run; `USE_IMAGES`/`cmd_use` in-container x86_64
  is a later refinement.
- **kbuilder image rename:** the clang-universal `like_kbuilder_arm64` builds x86_64 fine; the
  misnomer rename is deferred (ROADMAP note).
- **TCG performance:** x86_64 TCG is slow by nature; not optimized here.
